# 从业务到工作台设计

## 1. 理解与建模

在 `flows/<flow-id>/BRIEF.md` 记录角色、业务目标、成功标准、设备、数据实体、权限、入口、主路径、分支、完成条件与返回路径。每一步说明触发动作、前置条件、成功结果、失败恢复和加载/空/错误/禁用状态。

只询问会改变信息结构、流程或视觉方向的问题。已有明确答案直接沿用，其他合理假设写入 BRIEF。

## 2. 主题与视觉方向

任何概念图之前先填写 `DESIGN.md` 和 `tokens.json`。定义语义颜色、字阶、间距、圆角、阴影、栅格、导航框架、图像、动效和焦点规则。

方向未定时用同一代表页面和同一业务内容生成三张完整概念图。用户确认前保持 proposed；确认后升级主题版本并记录基准图。

## 3. 组件规范

检索 `components/index.json` 的 scope、excludes、tags 和版本，读取候选组件 MD。区分直接适用、需要业务适配和不适用。只有用户同意后，才把重复模式注册为系统组件规范。

组件规范说明何时使用、何时不用、组成、变体、状态、Token 绑定和可调整项。页面差异写在 `component_usage[].adaptation`。

## 4. 图片与流程

先冻结主题和基准页，再生成无依赖页面；需要父页面背景的弹层最后生成。页面、modal、drawer 和状态各自一张图，使用稳定 page ID 和递增 `image_revision`。

`flow.json` 记录真实页面、transition 和 annotation。画布排列写入 `layout.json`，不得为了视觉顺序虚构业务关系。

## 5. 发布与迭代

运行 `validate` 后在工作台检查流程切换、连接线、跨流程出口、图片、标注、Tokens、组件引用。收到修改意见后创建新图片版本并保留历史资产。
