# 设计画布性能审计 · 2026-10-04

## 结论

当前画布存在可以稳定复现的性能问题，瓶颈同时涉及项目数据、交互计算、主线程栅格化和 GPU 同步。单看“10,000 个矩形在已经缓存的区域平移”会明显高估完整编辑器的流畅度。

当前链路是 React 编辑界面 → 保留场景/空间索引 → Canvas2D 节点与瓦片栅格化 → WebGL2 纹理合成。GPU 合成已存在，但场景更新、快照、布局与生成瓦片仍会阻塞主线程。

测试代码与原始数据见本目录和 `apps/web/tests/performance/`。本报告针对当日工作区的生产构建，测试页直接调用现有渲染引擎与真实 `DesignEditor`。

最终基线包含 **419 个完成的测量阶段、六组测试**：引擎 134 项、完整编辑器 165 项、生命周期 3 项、快照对照 30 项、DPR/重复压力对照 60 项、真实空白页面三轮共 27 项。另保留早期完整编辑器、快照对照结果，以及崩溃前的部分捕获。完成阶段不代表性能达标。

## 环境与方法

- Windows；Intel Core i5-12600KF，16 逻辑线程，约 31.8 GiB 物理内存。
- Chromium 154；ANGLE / NVIDIA GeForce GTX 750 Ti / D3D11，实际启用 WebGL2。
- 浏览器 1280 × 720、原生 DPR 1；引擎视口 960 × 640；编辑器实际画布 785 × 606。
- 空闲 rAF 约 180 Hz（5.6 ms）；输入每个 rAF 发出一次。60 Hz 的帧预算为 16.7 ms，120 Hz 为 8.3 ms，180 Hz 为 5.6 ms。
- 本任务未在性能测量期间并行执行构建、类型检查或其他压力测试，没有 CPU 降速或网络模拟。系统其他后台负载没有隔离，因此保留重复测量范围，不将单次结果推广到其他机器。
- 动作同步耗时、rAF 帧间隔、长任务、编译/绘制/查询/GPU 提交/项目序列化分别计量。CPU 调用耗时与 rAF 频率均不能当作实际屏幕呈现 FPS。
- rAF 间隔仅采集输入循环；结束后额外等待三帧，继续收集函数计时与长任务，但不将这三帧纳入 interval 分位数。单次异步操作可能在收尾阶段继续绘制，因此必须结合 draw/long-task 数据，不能把第一帧间隔当作操作完成延迟。
- 连续阶段通常有 45～60 个样本；冷启动、按下、提交等单次阶段只有一个样本。关键缩放/高像素负载/图片快照场景另做三轮对照。不能用单次测量推断稳定 p95。
- 编辑器使用合成输入，取消合成 pointerId 的原生捕获，保留真实事件处理、React 更新、绘图、撤销和文字编辑；结果有几何、提交、文本断言。测试不调用项目保存 API。
- 原有本地页面为 0、40、22、23、40 节点。另构造分散/密集矩形、文字、图片、阴影/模糊、路径、组件实例、重叠、编组等场景，节点数最高 10,000。

## 已确认的问题与优先级

### P0：整项目快照和整页 JSON 比较放大内嵌图片数据

`DesignEditor.tsx:1101` 在按下拖动时 `structuredClone(project)`，`:1643` 在松手时对两个完整 `pages` 做 `JSON.stringify` 后比较，`:637` 提交时再次深拷贝完整项目进入撤销历史。撤销/重做也会深拷贝项目（`:673`、`:686`）。

上传图片本来就通过 `FileReader.readAsDataURL` 写入节点（`:1397`），因此“项目中存在大图片字符串”与实际功能有关。快照复制的是整个项目，不只是当前移动节点。页面更多时，受影响的数据范围还会扩大。

在中断前捕获的 5,000 节点内嵌图片压力场景中：按下耗时约 679 ms；松手同步动作约 2,875 ms，下一帧间隔约 3,822 ms。JS 堆近似值由按下前 410 MiB 增至按下后 832 MiB、提交后 1,268 MiB，后续测试页面崩溃。

崩溃是实际观察结果，但未取得浏览器的 OOM/进程退出诊断，不能把内存不足写成已证实的唯一崩溃原因。崩溃前只恢复了部分阶段，见 `2026-10-04-embedded-partial.json`；不把它计为完整通过。

建议先将图片字节移出节点/撤销快照，以稳定资源 ID 引用；手势记录变更集合或增量补丁；结束时用实际变更标记判断是否提交。撤销记录变化及必要的结构共享，不再复制整个项目。

### P1：批量选择启动存在平方级查找

`DesignEditor.tsx:1096` 调用选区根节点计算前还逐 ID `page.nodes.find`；`packages/editor-core/src/nodes/hierarchy.ts` 的 `rootSelection` 又对每个 ID 做 `nodes.find`，祖先查找仍遍历数组。大选区启动前有多轮线性查找嵌套。

第一轮有效完整编辑器测试中，10,000 个普通矩形全选后按下拖动约 511 ms，其中项目深拷贝仅约 7.4 ms；最终轮同步阻塞 2,471.2 ms，其中深拷贝 24.7 ms。虽然绝对值波动较大，两轮阻塞均主要发生在开始绘制之前，且这个场景不含图片。

建议建立复用的 `id → node`、`parent → children` 索引，以及选区 Set；把根节点/后代收集改为索引遍历，并缓存单次手势的结果。

### P1：编组与批量移动触发整场景更新和整屏重绘

`scene.ts:130` 的叶节点路径仍扫描全部节点；`:164` 复制 entries 和 nodes Map；父节点变化走完整层级编译。变化超过阈值时（`:159`、`:232`）全量失效瓦片。

5,000 子节点编组持续拖动，每帧重新生成节点对象、编译变换、维护索引并重新绘制可见瓦片。有效引擎基线中 p95 同步动作 94.2 ms，p95 重绘 12 个瓦片、5,424 个绘制条目。完整编辑器最终轮的编组拖动 rAF p95 为 266.7 ms；10,000 矩形的批量拖动最慢帧为 699.9 ms。编组测试中按下默认选中父组，Ctrl 按下的后续阶段选中叶节点，不能把两次拖动直接解释为吸附开关的 A/B 对照。

建议手势中使用临时容器/选区变换，优先复用子树绘制结果；结束时统一提交节点坐标。场景更新接收明确的变更集合，并把几何缓存与外观缓存分开，避免移动坐标时丢掉文字、图片和效果的外观缓存。

### P1：首次显示与缩放跨档集中重绘，GPU 提交包含同步等待

`tiles.ts:33` 以 `2 ** ceil(log2(pixelsPerUnit))` 选分辨率档位；第一次跨过档位边界会创建、绘制并上传另一套瓦片。所有脏瓦片在 `engine.ts:385` 的同一绘制调用中完成。

`compositor.ts` 每个脏瓦片调用 `texImage2D`，有上传时在 `end()` 调用 `gl.getError()`。计时中这个同步查询可能占据显著时间；该耗时包含驱动/浏览器进程等待，不能解释为纯 JavaScript 或 GPU 内核耗时。

有效引擎基线：10,000 矩形冷绘制 79.6 ms；同场景连续缩放 p95 只有 1.5 ms，但最慢单次 61.6 ms；图片场景跨档最慢 81.9 ms。平均值和 p95 都可能隐藏首次跨档卡顿。

完整编辑器自动适配画布会同时显示更多内容。最终轮 5,000/10,000 混合节点挂载同步耗时分别约 4.61/5.66 秒，10,000 混合节点缩放最慢帧约 2.44 秒。图片使用短 Blob URL，这部分开销独立于内嵌字符串快照问题。

建议分帧补齐新分辨率瓦片，先展示已有层级；对效果密集视图限制单帧栅格/上传预算；评估 GPU 错误查询的频率与非阻塞处理；验证重复初始化失效是否造成额外冷绘制。保持当前完整帧作为过渡，避免交互一直等待全部细节完成。

### P1：空白画布也会因相机状态、UI 更新与布局发生卡顿

本地真实空白页为 1440 × 1040，节点数为 0。补齐完整品牌静态资源并确认图片解码后三轮测试：缩放 rAF p95 为 **77.9 / 66.6 / 72.2 ms**，最大观测间隔 **127.8 / 94.5 / 94.5 ms**；对应 `engine.draw` p95 仅 **2.7 / 2.0 / 2.2 ms**。

每轮 60 次缩放输入都触发 120 次 `engine.setView`。`useCanvasViewport` 先更新 camera，再在 layout effect 中更新 origin，引发两次相机绘制；空白页的长动画帧还记录了 MessagePort 回调及同步样式/布局工作。仅减少场景节点或更换合成后端不能解决这条交互链路。

这确认了“小画布也卡”的问题存在于当前 UI/视口路径；尚未用 React 逐组件采样把额外耗时精确分摊到每个组件或空状态布局规则。建议先合并相机与 origin 的提交，将高频视口操作从整个编辑器的 React 更新中解耦，并进一步检查空状态随缩放变化的容器布局。

### P2：侧栏数据派生与诊断统计仍进入热路径

`previewProject`（`DesignEditor.tsx:624`）每次手势更新都设置编辑器顶层状态；`VirtualLayerList.tsx:70` 在 nodes 数组变化时重建图层行索引；滚动/缩放通过 `useCanvasViewport` 更新 React 相机与 origin，再于 CanvasRenderer 的 layout effect 同步绘制。

图层列表已经虚拟化，实测仅约 30 个图层行 DOM。减少 DOM 数量这一项已经存在，仍需减少每帧数据派生、组件更新与布局提交。

第一轮 5,000 混合节点拖动 rAF p95 33.3 ms，而 `engine.draw` p95 2.5 ms；这说明完整 UI/事件调度链路还有额外成本。但两个 p95 不能相减作为 React 的精确耗时，当前计时并未逐组件剖析 React。

`engine.ts:406` 为更新 `visibleNodes` 统计，每次内容绘制都会再查询一次可见节点。10,000 矩形的 45 次缓存平移中，该类空间查询累计约 40.9 ms；这时瓦片重绘和纹理上传均为零。建议将非必要统计采样化，并拆分交互、画布与侧栏状态订阅。

## 结果使用边界

本报告是本机真实 GPU 上的可复现基线，未覆盖其他浏览器、物理高分屏、低端移动设备、触控/输入法、网络保存、Agent 并发工作或外部图片网络延迟。单独挂载编辑器不包含整个应用的路由和服务端保存延迟。

JS 堆来自浏览器近似统计；缓存字节为引擎估算，均不等于进程总内存或实际显存。DPR 2 对照只验证双倍 backing-store 的工作量。

修复优先顺序：空白画布的相机/UI 更新与图片资源/撤销结构优先处理 → 批量选区索引 → 手势中的编组/选区临时变换 → 分帧瓦片更新与 GPU 同步 → 侧栏派生和统计采样。每项修复都应使用同一场景复测，保留 p95、最大帧间隔、长任务、资源体积与操作正确性断言。

建议下一轮优化以 60 Hz 为最低验收线：空白画布/常规单节点交互 rAF p95 ≤16.7 ms、最大间隔 ≤33.4 ms；60 次缩放最多提交 60 次相机更新；单次按下/提交不出现 >50 ms 长任务；10,000 节点选区启动摆脱平方级增长；移动相同图片不复制其字节进入每份历史。高刷新率目标应另按 8.3/5.6 ms 帧预算复测。
